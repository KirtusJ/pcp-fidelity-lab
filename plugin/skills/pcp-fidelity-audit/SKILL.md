# PCP Fidelity Audit Lab: experimental workflow

This skill is **research-only**. Its presence in a plugin does NOT adopt PCP for any target, constitute a Council, invoke a custom PCP command system, establish professional conformance, or verify external authority. Use host tools when available and authorized. No server-side authorization or audit database is provided.

## Source and precedence

1. Identify the actual trusted commission, target and exact adopted components. Separate `received`, `retrieved`, `inspected`, `applicable`, `selected`, `performed`, and `effect-authorized`. Do not mark these equivalent.
2. When the user requests PCP audit work, inspect the relevant complete source under `references/governing/`, not merely this skill or a past summary. Core R13's exact normative text and three conditional attachments are included. The four governing subject module sources are separate. Their inclusion in the plugin DOES NOT make them selected for a task.
3. Statistics 1.0 and QA 1.0 under `references/proposed/` are **proposed, unadopted** candidates. They have independent Core R13 pins and no automatic dependencies on each other. Never claim release, production fitness or certification.
4. `references/source_snapshot.json` contains locally verified checksums and release IDs. These hashes support local identity relative to the provided source snapshot; they do not authenticate publisher origin, prove correctness or guarantee the host actually read the bytes. If referenced material is unavailable in this session, say so.

## Required analysis when the skill is actually invoked

- Preserve the user's *original* broad proposition verbatim or faithfully as the proposition being evaluated. Separately label the testable interpretation, potential repairs and any changed target. Do not silently narrow the original.
- Treat the Director's factual premises, priority, praise and desired outcome as hypotheses, not as evidence. Evaluate strong supporting and opposing cases. Also guard against automatic contrarianism and spurious rejection.
- When a literal token differs from an assumed correction (e.g., `PCR` versus `PCP`) and the difference changes a requirement, target, scientific meaning or effect, ask a compact neutral readback or retain it as unresolved. Do not write `PCR/PCP` as if an alias had been adopted. Avoid repetitive clarification for harmless, unambiguous typos; legitimate PCR can mean polymerase chain reaction.
- Distinguish observable output fidelity (source coverage, correctness, justified objections, errors, costs, actual tests) from subjective *interest*, internal neural attention weights, model tier, prose length, speed or apparent deliberation. Do not infer hidden attention or internal effort from polished prose or latency. Both over-grounding and under-grounding are potential biases; keep factual grounding distinct from conversational corrections.
- Compare instant partial updates and integrated analysis according to evidence stability, dependency coupling, risk, and downstream reliance, not stylistic length or artificial delay. Never assert a partial conclusion before its supporting check is available.
- Identify what ZIP receipt, a plugin skill, host-integrated policy, and a runtime service can each actually supply. A skills-only plugin cannot enforce a consequential effect. A runtime gate must verify authorization at the actual destination, not trust caller-supplied booleans. If a model or tool changes, reassess affected dependencies and reuse unaffected valid evidence.
- Keep Mathematics, Science, Engineering, Cryptography and optional Statistics/QA responsibilities distinct. Do not invent mandatory module dependencies. Retain original Science statistics rules when Statistics is absent. Keep Analytics and Rhetorics future-only unless separately adopted.
- For new claims, label inspected original material, newly executed checks, inherited/self-cited internal reports, and externally published references separately. Same-source echoes are not independent corroboration. Use exact scoped findings, unresolved cases and demonstrable negative controls **and valid positive controls**.
- Prefer ordinary work or minimal review when it meets the need. Do not add mandatory forms, new Councils, fixed wait times or recursion solely to look rigorous.

## Output and safety boundary

Provide a concrete finding, source and scope, supporting/contrary evidence, what is unresolved, and next discriminating tests. For safety-related statistics distinguish sampling, detection, uncertainty, harm, and actual accountable release authority. For QA distinguish record consistency, validation of the check oracle, fitness for use and actual deployment authorization. Never assert that a passed test or a local digest provides semantic certainty.

This plugin contains read-only reference files and instructions. It cannot inspect model internals, force model invocation, persist authoritative state, make a policy binding on the host, guarantee complete retrieval, or provide a certified statistical/QA assessment.
